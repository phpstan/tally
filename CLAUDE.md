# Tally – notes for coding agents

Tally benchmarks PHP code by counting instructions, cycles, and memory under CodSpeed's CPU simulation instead of measuring time. CodSpeed's Valgrind is required: there is no mode that measures without it. Releases include builds of it and of CodSpeed's instrument-hooks library, so a project needs no CodSpeed setup. Benchmarks are `bench*` methods of classes in `*Bench.php` files; their expected numbers live next to them, in `#[Expected]` attributes or in an `ExpectationSource` a data provider attaches to a data set. See README.md for how it is used.

## Layout

- `src/Attribute` – the attributes benchmark classes use: `Expected` (a method without a data provider), `ExpectedFor` (one data set), `Complexity` and its presets (how the instructions grow), `Warmup`, `Before` and `After` (hook methods), `DataProvider`, and the tolerance policies `RelativeTolerance` and `DurationTolerance`.
- `src/Expression` – the expression language of complexity classes, all pure: `Lexer` (tokens with offsets), `Parser` (recursive descent into the `Node` tree, sealed), `Printer` (the canonical form, parsing it gives the same tree), `TypeChecker` (finds what the parameter types reveal, through `ValueType`), `Evaluator`, and the `MathFunction`s of the `FunctionLibrary`. Every mistake is an `ExpressionException` that quotes the expression and underlines the part that is wrong; `ExpressionErrors` words them the same for the checker and the evaluator.
- `src/Complexity` – `ComplexityClass`, the interface of `#[Complexity]` and its presets (`#[Linear]` and the others, which compose a `Complexity`), and `GrowthPoint`, where a case is on its growth curve. `Discovery\GrowthPoints` computes them at discovery, `Comparator::compareGrowth()` compares a case with its base. These cases have no numbers to accept.
- `src/Quantity` – `QuantityFormat` formats and parses numbers with units (`3.119B`, `44.49MiB`).
- `src/Expectation` – where expected metrics are stored. `ExpectationSource` is the interface: `read()` the expectation, `file()` the file it lives in, the pure `rewrite(code, metrics)` that returns the file's code with new expectations, and `location()`, which throws `ExpectationException` when the source cannot be rewritten. `AttributeExpectations` implements it for `#[Expected]` and `#[ExpectedFor]` through `ExpectedAttributeRewriter`, the pure code-to-code rewrite, and `Tokens`, the token list it walks. `ExpectationChanges` plans the rewrites of many cases (pure): one `FileChange` per file with every case in it, in a `ChangePlan` together with the cases that failed. `ExpectationFiles` reads and writes the files.
- `src/Discovery` – `DirectorySuiteLoader` finds and loads `*Bench.php` files (I/O), `CaseExpander` turns one method into its cases (pure, works on reflection); `hooks()` finds a class's `#[Before]` and `#[After]` methods once per class, because scanning them for every benchmark method made loading a class quadratic in its size. `AttributeFactory` creates every attribute Tally reads: it checks the arguments against the attribute's constructor first (names, count, types through `ValueTypeCheck`, as under strict_types), so a mistake is an `InvalidBenchmarkException` naming the argument, not a PHP error. Everything a benchmark author can get wrong, including a file that does not load and a data provider that throws, ends as an `InvalidBenchmarkException` that names the benchmark or file; PHP errors with stack traces are bugs. `ArgumentResolver` checks that a method takes the arguments of a data set (a hook the leading ones) and `ConstructorArguments` that a constructor takes only `Meter` and `ScratchDirectory`; discovery checks both, so a mismatch fails `tally list` instead of the worker.
- `src/Selection` – `CaseSelector` implementations: `FilterSelector`, `ShardSelector` (longest-processing-time sharding by expected instructions). Both keep a case compared by its growth with its base: the filter adds the base, the shards keep a method's cases together.
- `src/Runner` – running one case in this process. `CaseRunner` calls the hooks and warm-up uncounted, then counts a `#warmup` span, an empty `#baseline` call, and one call of the benchmark, and subtracts the baseline's memory. The `#warmup` span exists because the first counted span costs about twice as much as later ones. `MeterSession` is the `Meter` the benchmark object gets in its constructor, one per case: every call `CaseRunner` makes is a span of it with its own `Counter` (`CodSpeedCounter` over `InstrumentHooks` for the counted ones, `IdleCounter` for hooks and warm-up), and it measures memory above the start of the span through `Memory`. `FfiInstrumentHooks` is the only class that calls C.
- `src/Comparison` – `Comparator` turns a case's expectations and measurement into a `CaseComparison` of `MetricComparison`s with a `Status`. `TolerancePolicy` is implemented by the tolerance attributes; `CaseExpander` picks the method's, else the class's, else ±10 %. `Percent` formats shares.
- `src/Report` – `Report` groups comparisons into `Section`s by their worst status. Renderers are pure and return strings: `ConsoleReport` (summary and full table, with or without colors), `MarkdownReport` (GitHub job summary), `GitHubAnnotations` (workflow commands). `Rows` and `TextTable` lay out the tables. Cases measured without an expectation become `NewExpectations`: `ExpectationsPatch` renders the planned file changes as one patch with `UnifiedDiff` (the hunks GNU `diff -u` prints, applicable with `git apply`), so a contributor adds a benchmark without numbers and copies the expectations from the CI output. `RelativePath` makes paths relative to the working directory. The golden files in `tests/Unit/Report/golden` are the expected output; regenerate them only when the output changes on purpose, and read the diff.
- `src/Result` – `MeasurementJson`, the format of a measured case in results files; `ResultsDirectory` reads and writes a directory of them; `CallgrindProfile` reads the instructions and estimated cycles of each named part of a profile CodSpeed wrote.
- `src/Process` – a generic process pool. `ProcessPool` runs `Job`s, each a list of `ProcessCommand` steps that run while each succeeds, in parallel, and kills a step that exceeds its time limit with all its descendants through `ProcessKiller`. `ProcessTable` is the pure part: parsing `/proc/<pid>/stat` and finding descendants. Descendants matter because killing `codspeed` leaves Valgrind running.
- `src/Execution` – measuring a case in worker processes. `CaseJobs` builds a case's job (a native run, then a run under CodSpeed's Valgrind with the options of `codspeed run --mode=simulation`, sharing a scratch directory) and reads what the job left. `WorkerCommandLine` builds the commands, `CaseOutcome` turns the runs and the profile parts into a `Measurement` (both pure). `CodSpeedInstallation` finds the build of Valgrind and instrument-hooks for the platform in `codspeed/linux-<machine>`, whose tools the workers find through `VALGRIND_LIB`, `DirectoryRemover` cleans up the work directory.
- `src/Cli` – `Application`, the commands (`list`, `run`, `compare`, `accept`, and the hidden `worker` that `run` starts), `ArgumentParser`, `Input`, `Output`. `ReportOutput` writes the report, with the patch for cases without expectations, and, in GitHub Actions, the annotations (relative to `GITHUB_WORKSPACE`) and job summary. `run` checks that every selected case's expectations can be rewritten before it counts anything; `accept` writes each file once. `ApplicationFactory` is the composition root; `bin/tally` passes it the streams, the environment, and the binaries the workers run. Every error goes through `Output::error()`: the first line says what is wrong (bold red on a terminal), the lines after it what to do, such as `Run tally list --help for its options.`; an unknown command or option suggests the closest name through `Text\ClosestName`.
- `src/Text` – `ClosestName`, the "did you mean" suggestion for a mistyped name of a command, option, variable, function, or key.
- `src/` root – value objects shared by everything: `Metric`, `Metrics`, `CaseId`, `BenchmarkCase`, `DataSet`, `Measurement`, `ScratchDirectory`, `Configuration`, and the `Meter` interface.
- `bin/tally` – finds the autoloader and runs `ApplicationFactory`.
- `bench/` – Tally's benchmarks of itself, listed in `tally.php`. They cover the code whose cost grows with the suite, a benchmark file, or a profile, and that runs once per case or once per worker: locating and rewriting expectations, planning and diffing new expectations, expanding cases, sharding, reading profiles, and rendering reports. `SuiteSource` generates the code and cases of large benchmark classes as their input. Build inputs in data providers and before methods, which are not counted, and keep the counted call to the one method being measured. `#[Warmup(1)]` keeps autoloading out of the count.
- `examples/` – short, artificial benchmarks for README.md, one feature each. `examples/Scripts` shows a data provider with its own `ExpectationSource`, which keeps the numbers in a comment at the top of each script. Keep them readable over realistic; real measurements of Tally belong in `bench/`. CI runs them under CodSpeed next to `bench/`, so they stay valid.
- `build/` – scripts for the build, such as the coverage check. `build-codspeed.sh` builds CodSpeed's Valgrind (Callgrind only, static launcher) and instrument-hooks at pinned commits into `codspeed/linux-<machine>`, which `1.x` ignores. `build-release.sh` turns `1.x` into the `release/1.x` tree by committing the builds of both platforms; CI pushes it on every push to `1.x`, and releases are tagged there. `check-release.sh` installs a release tree into a new project with Composer and counts a benchmark, which CI runs on every pull request on x86_64 and aarch64. `build/PHPStan` holds Tally's own PHPStan rules and `BenchmarkUsageProvider`, which tells the dead code detector about the methods Tally calls through reflection. `build/stubs` holds the stubs for what PHPStan cannot see, such as the C functions FFI calls.
- `tests/Unit` – pure logic, no file system, processes, or network. `tests/Integration` – adapters and the CLI. `tests/Fixtures` – benchmark classes and configuration files the tests load; excluded from PHPStan and the coding standard because some are invalid on purpose.

## Design rules

- Every class is `final`. Behavior is composed from injected collaborators, never inherited. Interfaces are for real variation points (`ExpectationSource`, `CaseSelector`, `Command`), not for every class.
- Services are stateless and get their collaborators through the constructor. No singletons, no static service methods, no service creating another service with `new`. `ApplicationFactory` decides which implementation each service gets.
- Value objects (`Metrics`, `CaseId`, `DataSet`, `Measurement`, `Configuration`, `Tokens`) are immutable: `readonly` properties, `with…()` methods that return a copy. `MeterSession` is the one mutable object, because a benchmark pauses and resumes it; it lives for one case.
- No optional parameters and no default values, in `src` and `tests` alike: every parameter is required and every call passes every argument, and properties get their values in the constructor. Attributes too: `#[Expected]` takes all three metrics. A value used by default, like the 10 % tolerance, is a named constant where it is chosen. PHPStan enforces this with the rules in `build/PHPStan`.
- Keep pure logic and I/O in separate classes. Logic takes everything it needs as arguments and returns its result (`ExpectedAttributeRewriter` takes code and returns code); a thin adapter reads and writes (`AttributeExpectations` reads and writes the file).
- No runtime dependencies besides PHP 8.2 or later, so projects that support old PHP versions can require it. PHPStan checks the code for the whole range (`phpVersion` in phpstan.neon), so a newer function or syntax fails the build. Dev dependencies are fine, and may need a newer PHP: CI tests on 8.2 with PHPUnit 11 and without Infection.
- Errors the user causes and can fix (invalid benchmark, bad CLI usage, unparsable quantity) are checked exceptions extending `Exception` and are declared with `@throws`. Errors that only a bug in Tally causes extend `LogicException`.
- Public API for benchmark authors and extensions is marked `@api`. Everything else may change.

## Tests

- No mocks. Test logic through its inputs and outputs, with data providers that name each case. A fake implementation of an interface is fine where an adapter is needed (`tests/InMemoryExpectations.php`).
- External programs are replaced by fakes with the same interface: `tests/Fixtures/CodSpeed/valgrind` runs the command like Valgrind's launcher and writes a profile with the counts from `TALLY_FAKE_COUNTS`; `tests/Fixtures/InstrumentHooks/recording.c` (built by `tests/InstrumentHooksFixture.php`) records the calls instead of talking to Valgrind.
- `tests/InProcessTally.php` runs the application in the test process, so coverage counts it. Coverage collection allocates memory, so assertions on measured memory run `bin/tally` in its own process.
- Unit-test pure classes thoroughly. Integration-test adapters and the CLI end to end (`Application` through `ApplicationFactory`, and `bin/tally` in a process).
- Assert exact outputs, such as whole strings and exact exception messages, not substrings.
- Write the test first. Every line of `src` is covered and every mutant is killed; when a mutant survives, add the test that tells the two versions apart, or restructure the code when the mutant is equivalent (an initial value that is always overwritten, a check another check already makes). No `@infection-ignore-all`.

## Checks

All must pass before a commit:

```bash
make lint       # parallel-lint
make cs         # phpstan/build-cs, make cs-fix fixes what it can
make tests      # PHPUnit
make phpstan    # level max, strict rules, bleeding edge, dead code detector, checked exceptions
make coverage   # pcov, fails below 100 % of lines
make infection  # mutation testing of the whole codebase, fails below 100 % MSI
make bench      # bench/ under CodSpeed's Valgrind, builds it with build/build-codspeed.sh first
```

`make cs-install` clones build-cs. PHPStan runs with no ignores and no baseline: fix the types. The dead code detector reports unused code; delete it, or mark it `@api` when it is public API. A stale result cache of the dead code detector makes PHPStan fail with "DCD cache file not found"; `make infection` clears the result cache first, run `vendor/bin/phpstan clear-result-cache` before other runs when it happens. CI runs the lint and the tests on PHP 8.2 to 8.6, the rest on 8.5 and 8.6; Infection runs on the whole codebase on pushes and on the changed lines in pull requests. The Benchmarks job runs `bench/` under CodSpeed on a pinned runner, because the counts depend on the PHP build. Take expected numbers from that job, not from a local run: a benchmark without them gets a patch in the job's output, and changed numbers get `tally accept` with the `tally-results` artifact.

## Conventions

- Every file starts with `<?php declare(strict_types = 1);`, tabs for indentation.
- Concise technical English in code comments, docs, and commit messages. Comments say why, not what.
- Commits are small and explain why. One logical change per commit, its tests included.
- README.md documents every command, option, and attribute. Change it together with them, with output copied from a real run.
- Keep this file up to date when the layout or a rule changes.
